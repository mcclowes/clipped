# Clipped — holistic code review

**Reviewer:** principal engineer, first week on this codebase, asked to be as critical as possible.
**Scope:** every Swift file under `Clipped/Sources` and `Clipped/Tests` (~12.7k lines), plus `project.yml`, entitlements, `Makefile`, CI, and the repo layout.
**Tree reviewed:** `main` @ `7803224` (v1.7.0), working tree clean.
**Method:** full manual read of the ingestion, persistence, crypto, concurrency, and view layers. Every finding below was verified against the current code — line references are to this commit.

---

## Read this before the findings list

Two things need saying up front, because a review that misrepresents its subject is useless.

**First: this is good code.** The service decomposition is real (`ClipboardManager` genuinely is a coordinator, not a god object), the actor boundary around `HistoryStore` is textbook Swift 6, encryption-at-rest exists at all, `[weak self]` hygiene is essentially perfect, cancellation is propagated correctly where it matters, and the test suite uses modern Swift Testing properly. Someone here knows what they are doing. I found **no data races** and **no retain cycles**.

**Second: there are already three code-review documents committed at the repo root** — `CODE_REVIEW.md`, `PRINCIPAL_REVIEW.md`, and `code-review.md`, 1,870 lines between them — and they are all stale. PR #102 fixed a large fraction of what they describe, but the documents still read as open findings. A new engineer reading them would spend a day chasing ghosts. **See §G1; this is itself a process problem worth fixing.** This document deliberately re-derives everything from the code rather than trusting those files.

So this review is not "the architecture is wrong." The architecture is fine. The problem is a consistent pattern, and it is the single most useful thing for the team to internalise:

> **A protection or feature is implemented in *one* code path, and then a second code path is added later that reaches the same data without it.**

Reveal is authenticated in the panel — and not in the history window or sticky notes. Ingestion applies password-manager policy, secret detection, size caps, and OCR — and the screenshot watcher inserts straight into history, bypassing all four. The save-blocking guard protects history from being overwritten by a failed load — and the recovery button that clears the guard also throws away the data it just recovered. Persistence loads at bootstrap — and the setting that enables persistence never triggers a load.

Every one of the top findings is that shape. It is not a knowledge gap; it is a *habit* gap. The fix is a review question: **"what else can reach this data, and does it go through this check?"**

### Severity legend

| | Meaning |
|---|---|
| 🔴 **Critical** | Silent data loss, a security control that doesn't hold, or a headline feature that is non-functional. Fix before the next release. |
| 🟠 **High** | Wrong behaviour under believable, non-adversarial conditions. |
| 🟡 **Medium** | Real defect, performance cliff, or divergence between what the code claims and what it does. |
| ⚪ **Low** | Polish, latent trap, or an inconsistency that will bite later. |

## A. Data integrity and persistence

The persistence layer is the most carefully engineered part of this codebase, and it still has two ways to permanently destroy a user's history. Both were introduced *by* the code that was added to prevent data loss — which is exactly why they're worth studying.

### 🔴 A1. Turning "Persist history across reboots" on mid-session silently destroys the saved history

This is the finding I would block a release on.

`ClipboardHistory.loadPersistedHistory()` is gated on the setting (`ClipboardHistory.swift:188`) and is only ever called from `ClipboardManager.bootstrap()` at launch (`ClipboardManager.swift:124-129`). The Settings toggle at `SettingsView.swift:70` is a plain `Toggle` with **no `onChange` handler** — nothing observes the setting flipping.

Now trace a completely ordinary user journey:

1. User has persistence **on**. 200 items accumulate in `history.enc`.
2. User turns persistence **off** (privacy sweep before a demo, say). The file stays on disk — nothing deletes it.
3. User quits and relaunches. `loadPersistedHistory()` returns immediately at the guard; **nothing is loaded, and `HistoryStore.load()` is never called**, so `loadError` and `saveBlocked` are never set.
4. User copies three things during the session.
5. User turns persistence back **on**. No load happens.
6. The next copy calls `saveHistory()`. The guard at `ClipboardHistory.swift:230` now passes. `HistoryStore.save()` sees `saveBlocked == false` (step 3 never ran), encrypts the three in-memory items, and `writeAtomically` **overwrites `history.enc`** (`HistoryStore.swift:134-137`).
7. `deleteOrphanedImageFiles(keeping:)` (`HistoryStore.swift:132`) then deletes every encrypted image sidecar whose UUID isn't in the three live items.

200 items and all their images are gone. There is no backup — `backUpUnreadableFile()` only fires on a *read* failure, and no read was attempted. The `saveBlocked` machinery, which exists precisely to stop `save()` clobbering data it couldn't read, is bypassed because it is armed exclusively by `load()`.

**Fix:** make the setting the trigger, not just a gate. `onChange` of `persistAcrossReboots` → when turning on, `await loadPersistedHistory()` (merging, per A2) *before* any save can run; when turning off, decide explicitly whether the on-disk file is retained or cleared and say so in the UI. Better still, have `save()` refuse to write whenever a load has not been attempted this session.

> **Lesson:** A guard that is armed by one code path protects nothing against a code path that skips it. When you write a "refuse to write if X" check, enumerate every way `save` can be reached and confirm X is initialised on all of them. Default-false state (`saveBlocked = false`) means "safe to write" — make the *unsafe* condition the default and prove your way out of it.

### 🔴 A2. The recovery flow throws away the data it just recovered, then overwrites the file

This one is subtle and worth reading slowly, because the individual pieces are all defensible.

`applyLoaded` deliberately refuses to clobber in-memory items (`ClipboardHistory.swift:221-222`):

```swift
if items.isEmpty { items = loaded }
if pinnedItems.isEmpty { pinnedItems = pinned }
```

That is correct for the *bootstrap* case it was written for — it stops an async load racing an early copy. But `retryHistoryLoad()` (`ClipboardHistory.swift:196-201`) reuses it, and the retry happens in a completely different state: the user has been running for a while, the alert is presented from the clipboard panel (`ClipboardPanelView.swift:283`), and by the time they open the panel and press Retry they have almost certainly copied something. So `items` is non-empty.

Sequence:

1. Keychain locked at launch → `load()` sets `loadError = .decryptionFailed`, `saveBlocked = true`, backs up the ciphertext, returns `[]` (`HistoryStore.swift:203-209`).
2. User copies a few things. Saves are correctly refused (`HistoryStore.swift:103-109`). Good so far — the guard is working.
3. User unlocks the Keychain, opens the panel, presses **Retry**.
4. `retryLoad()` → `load()` succeeds. It clears both `loadError` **and `saveBlocked`** (`HistoryStore.swift:229-230`) and returns all 200 entries.
5. Back in `ClipboardHistory`, `applyLoaded(entries)` runs — `items` is non-empty, so **the 200 recovered entries are discarded**.
6. The user sees the alert disappear and their history still missing. They copy something.
7. `saveHistory()` → `save()` → `saveBlocked` is now `false` → the 200-entry ciphertext is overwritten with the handful of in-memory items, and `deleteOrphanedImageFiles` removes their images.

The one action the UI offers as "this is the safe choice, nothing is overwritten until you choose Start fresh" (`ClipboardPanelView.swift:288-293`) is the action that arms the overwrite. The reassurance in the alert text is false.

`history.unreadable.enc` does survive (`backUpUnreadableFile`, `HistoryStore.swift:297-302`), so this is recoverable by a user who knows to look — but nothing tells them it exists.

**Fix:** `applyLoaded` needs a merge mode. On retry, union by `id` (preferring in-memory for items present in both, since those are newer) rather than the launch-time "don't clobber" rule. Then clear `saveBlocked` only after the merged set has been committed to memory. Add a test that copies an item, then retries a load, and asserts both the copied item and the persisted ones survive.

> **Lesson:** A helper written for one lifecycle moment usually encodes assumptions about that moment. `applyLoaded`'s `if items.isEmpty` is not a general rule — it's "we are still booting." When you reuse it from a second caller, ask what that assumption was and whether it still holds. Naming the assumption in the method (`applyLoadedAtLaunch`) would have made the reuse obviously wrong.

### 🟠 A3. "Clear history" doesn't clear the disk, and cleared items come back after a relaunch

`ClipboardHistory.clearAll` (`:145-154`) empties the in-memory arrays and calls `saveHistory()` — which returns immediately when persistence is off (`:230`). `HistoryStoring.clear()` exists and is fully implemented (`HistoryStore.swift:245-253`) but **has zero production callers** (verified by grep across `Sources`).

So with persistence disabled but a `history.enc` on disk from an earlier session: "Clear All" and the quick menu's "Clear history" (`ClipboardPanelView.swift:104-109`) empty the visible list and do nothing to the file. Turn persistence back on, relaunch, and everything the user believed they had destroyed is back.

Even with persistence *on*, clearing writes the surviving pinned items rather than calling `clear()`, so the semantics are "rewrite" not "erase" — no explicit removal of the file, the images directory, or `history.unreadable.enc`.

**Fix:** route both clear affordances through `historyStore.clear()` regardless of the persistence setting. A destructive action must reach the durable copy.

> **Lesson:** "Delete" that is implemented as "save the smaller list" is only a delete when saving is guaranteed to happen. Destructive operations should not be gated on a preference that governs *routine* writes.

### 🟠 A4. A failed legacy migration promises to preserve the plaintext, then the next save deletes it

`migrateLegacyPlaintext` has an explicit contract in its own comment (`HistoryStore.swift:378-380`): *"If decoding fails we leave the plaintext alone so the user can recover it manually."* On failure it logs and returns without touching `history.json` (`:384-387`). Correct.

But then `load()` falls through, finds no `history.enc`, and returns `[]` with `loadError = nil` (`:179-182`) — the failure is invisible to the app. The user copies something. `save()` runs, succeeds, and unconditionally executes:

```swift
if FileManager.default.fileExists(atPath: legacyPlaintextFileURL.path) {
    try? FileManager.default.removeItem(at: legacyPlaintextFileURL)
}
```
— `HistoryStore.swift:142-144`

The plaintext the migration deliberately preserved is deleted seconds later by an unrelated code path, and the user's pre-upgrade history is gone with no error ever shown.

**Fix:** track migration failure in state (`saveBlocked`, or a dedicated flag) so the cleanup in `save()` only fires when migration actually succeeded. The cleanup's precondition is "we successfully migrated," not "we successfully wrote."

> **Lesson:** Same pattern as A1. Two functions each behave correctly in isolation; the contract lives *between* them and nothing enforces it. If a comment describes a guarantee that spans functions, that guarantee needs to be represented in state, not prose.

### 🟡 A5. An item whose image sidecar fails to decrypt vanishes silently

`decodeContent` returns `nil` when `imageData` is missing for an `.image` entry (`HistoryStore.swift:664-670`), `toClipboardItem()` therefore returns `nil`, and `applyLoaded` skips it with a bare `continue` (`ClipboardHistory.swift:214`). No log, no counter, no user-visible signal. If a sidecar is corrupted or its write was interrupted, the item disappears from history and the app reports a clean load.

**Fix:** at minimum log a count of dropped entries; ideally keep the item as a placeholder so the user knows something was there.

### 🟡 A6. Orphaned encrypted image files accumulate forever when persistence is off

`deleteOrphanedImageFiles` only runs inside `save()` (`HistoryStore.swift:132`). With persistence disabled, saves never run, so image sidecars written during an earlier persist-on session stay on disk indefinitely — encrypted, but unbounded, and never swept. There is no size accounting anywhere for the `images/` directory.

### ⚪ A7. `fatalError` in a shipping initializer

`HistoryStore.init` calls `fatalError("Application Support directory not found")` (`:72`). On a machine where that lookup fails, a clipboard manager crashes on launch instead of degrading to memory-only. Prefer a failable init or an in-memory fallback.

## B. Security and privacy

The threat model here is unusually demanding: this app records **everything the user copies** — passwords, API keys, 2FA codes, private keys — runs with **the sandbox disabled** (`project.yml:35`), and holds a network-client entitlement. Hardened runtime is on, which is right. The problems are all in the same family: a control exists on one path and not on the others.

### 🔴 B1. The biometric gate on "Reveal" is bypassed by two other views

PR #102 added `authenticateAndReveal()` to `ClipboardItemRow` (`:221-235`) — `LAContext.evaluatePolicy(.deviceOwnerAuthentication)` before unmasking. That is the right control.

It is the only place it exists. Two other views render the same masked items and unmask them with a plain state flip:

- `HistoryWindowView.maskedPanel` — `Button { isRevealed = true }` (`HistoryWindowView.swift:659-661`)
- `StickyNoteView.maskedContent` — `Button { isRevealed = true }` (`StickyNoteView.swift:121-123`)

Both are reachable from the same row the auth gate protects: the row's own context menu has **"Open as sticky note"** (`ClipboardItemRow.swift:129-131`), and the history window is one click away in the bottom bar. Right-click a masked secret → open as sticky note → click Reveal. No authentication, same item, same bytes.

**Fix:** the mask + reveal decision belongs in one place — a small view model or a `RevealPolicy` type owning `isRevealed` and the `LAContext` call — consumed by all three views. Three copies of `(item.isSensitive || item.containsSecret) && !isRevealed` (`ClipboardItemRow.swift:215-217`, `HistoryWindowView.swift:572-574`, `StickyNoteView.swift:96-98`) is the tell that this was going to drift.

> **Lesson:** When you add a security control, grep for every other site that renders the same field. Three copies of a predicate means three places to remember, and you will not remember. Duplication of a *display* rule is a style problem; duplication of a *security* rule is a vulnerability with a countdown timer.

### 🔴 B2. Masking is cosmetic — every export path emits the plaintext with no auth and no mask check

Even with B1 fixed, the mask protects only the on-screen preview. None of these consult `shouldMask`, and all operate on the full unmasked content:

- **`exportItems`** (`ClipboardManager.swift:523-531`) joins `plainText` of *all visible items* — masked ones included — and puts the result on the system pasteboard. It is a single unguarded button in the panel's bottom bar (`ClipboardPanelView.swift:389-398`), labelled "Export visible items."
- **"Save as…"** (`ClipboardItemRow.swift:170-188`) writes the decrypted bytes to any location the user picks.
- **"Copy extracted text"** (`ClipboardItemRow.swift:104-108`) copies OCR'd text off an image — and the menu item is built for every image item regardless of mask state.
- **"Paste directly" / "Paste and match style"** inject the content into another app.

So the answer to "how do I read a masked secret without authenticating" is *click the export button*.

**Fix:** decide what masking means and enforce it at the model boundary. If it means "reading the content requires auth," then a single `contentForExport(item:) async throws -> ClipboardContent` that performs the auth check is the only way to get bytes out of a masked item, and every export path goes through it.

> **Lesson:** A visual mask is a hint, not a boundary. If the same object hands out its plaintext through a dozen accessors, no amount of UI can protect it. Boundaries live at the data access point.

### 🟠 B3. The screenshot watcher bypasses the entire ingestion policy pipeline

`ScreenshotWatcher.ingestScreenshot` (`:182-214`) constructs a `ClipboardItem` and calls `clipboardManager?.history.insert(item)` **directly** (`:205`), reaching past `ClipboardManager.ingest` entirely. Everything `ingest` does is therefore skipped for screenshots:

| Applied on copy (`ClipboardManager.ingest`) | Applied on screenshot |
|---|---|
| Password-manager policy / `isSensitive` (`:240-252`) | ✗ |
| `SecretDetector` scan (`:255-257`) | ✗ |
| OCR text extraction + its secret scan (`:271-273`, `:319-339`) | ✗ |
| 64 MB size cap (`PasteboardMonitor.swift:53, 182-185`) | ✗ |
| `trimExpiredItems()` (`:263`) | ✗ |

The consequences are pointed. A screenshot is *the* most likely way a secret enters this app — screenshotting a 2FA screen, a terminal with an env dump, a revealed password field. Those images are stored, persisted to disk, and never flagged. And the OCR feature added in #101, whose most obvious use case is "read the text in my screenshot," never runs on screenshots at all.

**Fix:** there should be exactly one ingestion entry point. Give `ClipboardManager` an `ingest(item:policy:)` that both the pasteboard monitor and the screenshot watcher call. The watcher's job is to produce a `ClipboardItem`, not to decide history policy.

> **Lesson:** Two writers into one store means two policy implementations, and the second one is always thinner. When you add a new source of data, wire it into the existing pipeline rather than to the pipeline's destination.

### 🟠 B4. Taking a screenshot overwrites whatever the user had copied

`ingestScreenshot` calls `clipboardManager?.copyToClipboard(item)` (`:208`) — every capture clobbers the system pasteboard. The user had a URL on the clipboard, pressed ⌘⇧4 to grab a reference image, and their URL is gone. The feature is opt-in, but nothing in the settings copy ("Capture screenshots to history", `SettingsView.swift:94`) says it will take over the clipboard.

Compounding it, "screenshot" is defined as *any* file with a png/jpg/jpeg/heic extension appearing in the watched folder (`ScreenshotWatcher.swift:229-235`). Point it at Desktop or Downloads — the obvious choices — and every saved image, browser download, and AirDrop receipt is ingested and force-copied.

**Fix:** make clipboard replacement a separate opt-in; filter on `screencapture`'s naming/metadata rather than extension alone.

### 🟡 B5. `copyText` creates history items with no secret detection

`copyText` (`ClipboardManager.swift:413-427`) inserts a fresh `.text` item with no `SecretDetector` pass. Its callers are "Copy extracted text" (OCR output — which may well be the secret the source image was flagged for) and "Copy Summary". So the laundering path is: image flagged `containsSecret` → copy its extracted text → a new, unflagged, fully searchable, persisted plaintext item.

**Fix:** every path that creates a `ClipboardItem` from text should run the same classification. Put it in the `ClipboardItem` factory, not in `ingest`.

### 🟡 B6. SSRF: the remaining gaps are honest but real

Credit where it's due — the current filter is a serious piece of work. `IPLiteral` canonicalises through `inet_pton` (`LinkMetadataFetcher.swift:238-252`), correctly unwraps IPv4-mapped, IPv4-compatible, and NAT64 embeddings (`:295-306`), and `hostResolvesToPublicAddress` validates **every** resolved A/AAAA record and fails closed (`:95-120`). The bypasses in the older review documents are genuinely fixed, and the test matrix at `LinkMetadataFetcherTests.swift:34-86` covers them.

Residual risk, accurately documented in the code's own comments (`:92-94`) and repeated here so it isn't forgotten:

- **Redirects are unvalidated.** `LPMetadataProvider` follows them internally with no per-hop hook, so `https://public.example/x` → `302` → `http://169.254.169.254/…` sails through. This is the big one, and it is not fixable while `LPMetadataProvider` is the fetcher.
- **DNS rebinding** — validation and the actual connection are separate resolutions (TOCTOU).
- **`fec0::/10` site-local** (deprecated but still routed on some networks) isn't in `ipv6Reserved` (`:295-313`).

**Fix direction:** to close redirects you need your own `URLSession` with a `willPerformHTTPRedirection` delegate re-running `hostResolvesToPublicAddress` on each hop, which means hand-rolling the metadata parse that `LPMetadataProvider` currently gives you for free. That is a real trade-off — but it should be a decision the team makes explicitly, not one it inherits.

### 🟡 B7. A test double ships in the production binary

`InMemoryKeyStore` (`KeychainKeyStore.swift:102-129`) lives in `Sources/Services`, so it is compiled into the shipping app. It's not reachable from production code paths, but a class whose entire purpose is "hold the history encryption key in a plain variable, never persist it" has no business in a release binary. Move it to `Tests/Mocks.swift` alongside every other double.

### ⚪ B8. Entitlements don't describe the app

`project.yml:35-38` requests `files.user-selected.read-only` while "Save as…" **writes** user-selected files, and `app-sandbox: false` makes the whole list inert anyway. It reads like an aspiration rather than a description. Either pursue sandboxing properly (and fix the read-only mismatch) or trim the list to what is actually load-bearing, with a comment saying why the sandbox is off.

## C. The clipboard pipeline — edge cases that were missed

This section answers the "what edge cases have not been spotted" part of the brief directly.

### 🟠 C1. Deduped items still trigger a network request and an OCR job

`ClipboardHistory.insert` returns early when the content is already pinned (`:96`):

```swift
if pinnedItems.contains(where: { $0.content == item.content }) { return }
```

The item is dropped. But `ingest` doesn't know that, and continues (`ClipboardManager.swift:268-273`) to schedule a link-metadata fetch and an OCR extraction for an item that is not in any collection. Both tasks run to completion — a real HTTP request to the URL's origin, a real Vision OCR pass — then look up the ID, find nothing, and discard the result.

For the link fetch that's a privacy leak as well as waste: the app contacts the origin server for content the user had already saved, and which it just decided not to store.

**Fix:** have `insert` return whether it accepted the item, and skip enrichment when it didn't. Or better — merge into the existing pinned item and enrich *that*.

### 🟠 C2. "Paste and match style" from the history window silently does nothing

`previousActiveApp` is set only by `captureFrontmostApp()`, called only from `StatusBarController.show()` (`:73`) — i.e. only when the **panel** opens. But `pasteMatchingStyle` is offered in the history window's context menu (`HistoryWindowView.swift:190`), and the history window has its own global hotkey that never goes through `show()` (`ClippedApp.swift:87-97`).

So: open the history window with ⌥⇧C, right-click an item, "Paste and match style" → `previousActiveApp` is `nil` (or stale from an earlier panel session). `pasteToActiveApp` then evaluates (`ClipboardManager.swift:474-489`):

```swift
let target = previousActiveApp          // nil
copyToClipboard(item, asPlainText: true)
Task {
    target?.activate()                  // no-op
    try? await Task.sleep(for: .milliseconds(120))
    guard !IsSecureEventInputEnabled() else { return }
    if let target, ... { return }       // target is nil, so this passes
    simulatePaste()                     // fires into whatever is frontmost — Clipped
}
```

With `target == nil` the guard falls through and ⌘V is synthesised into the **history window itself**. The user sees a copy happen and no paste. If a stale non-nil target exists, the pid check returns early and nothing pastes at all.

The 120 ms sleep is also a magic number racing the panel's own 400 ms dismissal animation (`ClipboardPanelView.swift:516-530`) — the paste is attempted while the panel is still on screen.

**Fix:** capture the frontmost app in one place that runs for every presentation path (panel, history window, both hotkeys), and treat "no target" as "don't synthesise a keystroke" rather than "paste into whoever's there."

### 🟠 C3. Secure auto-removal misses pinned items

`scheduleSecureAutoRemoval` removes by ID from one array only (`ClipboardManager.swift:292`):

```swift
history.items.removeAll { $0.id == itemID }
```

`togglePin` moves the item from `items` to `pinnedItems` (`ClipboardHistory.swift:109-121`). Pin a password-manager item inside the timeout window and the removal finds nothing — the secret stays in memory indefinitely. It won't reach disk (`isSensitive` filters it out of saves at `:232`), but "remove after 30s" simply doesn't happen, and the UI gives no indication.

**Fix:** remove from both collections. Better: a single `remove(id:)` on `ClipboardHistory` that owns knowing where items can live — this is the third place in the file that has to remember there are two arrays.

### 🟡 C4. Dedup does a full byte-compare of every image on every copy

`ClipboardContent` is `Equatable` with `case image(Data, CGSize)` (`ClipboardItem.swift:615-621`), and `insert` runs three content comparisons across the whole history (`ClipboardHistory.swift:96-105`). `Data`'s `==` short-circuits on length, so mismatched sizes are cheap — but same-size images (very common: repeated screenshots at the same resolution, the same asset copied twice) do a full memcmp, on the main actor, on the ingest hot path, for up to 500 items.

**Fix:** dedup on a cheap content hash (`SHA256` of the payload, or size + first/last KB) computed once at construction.

### 🟡 C5. Two search implementations that already disagree

Search is implemented twice:

- `ClipboardHistory.applyFilters` (`:58-89`) — handles `selectedFilter`, `searchableText`, and correctly excludes `extractedText` for masked items.
- `HistoryWindowView.displayedItems` (`:322-330`) — its own category enum, its own search, ignores `manager.selectedFilter` entirely.

They already differ (the window has no notion of the panel's filter; the panel has no notion of the window's app grouping), and any future change to search semantics — fuzzy matching, ranking, a new masked field — must be made twice or the two surfaces drift further.

**Fix:** one filtering function parameterised by criteria; both views call it.

### 🟡 C6. Rapid copies inside the poll window are still dropped, and the code measures the loss before discarding it

Polling `changeCount` at 2 Hz (`PasteboardMonitor.swift:50`) means copying A then B within 500 ms captures only B. The code computes exactly this and emits it as a signpost (`:120-124`):

```swift
let changeDelta = currentCount - lastChangeCount
...
Signposts.clipboard.emitEvent("PasteboardChange", "delta: \(changeDelta)")
```

then ingests only the final state. Knowing you dropped a copy and doing nothing about it is a strange place to stop. Either accept it and document the limitation in the README, or act on it — a `delta > 1` could at minimum warn, and macOS offers no push notification for pasteboard changes, so the honest answer is probably "document it."

### 🟡 C7. Re-copying an item loses most of its enrichment and orphans its image file

`insert` merges exactly three fields from the previous identical item (`ClipboardHistory.swift:100-104`): `linkTitle`, `linkFavicon`, `extractedText`. Dropped on the floor: `mutationsApplied`, `originalContent` (so "Restore original" disappears on re-copy), `detectedCategories`, `isDeveloperContent`, `customPasteboardTypes`, `containsSecret`.

`containsSecret` is the one that matters — a re-copy that arrives before the secret scan completes... actually the scan runs synchronously in `ingest` (`:255-257`), so the new item is re-scanned. Fine. But `isSensitive` is *not* re-derived if the second copy comes from a different app, and the categories/dev-flag are recomputed only for `.text` content in the monitor.

The new item also gets a **new `id`** (`:106`), so its encrypted image sidecar is written under a new UUID and the old one lingers until the next save's orphan sweep. For a workflow of repeatedly re-copying the same large screenshot, that's a churn of multi-MB encrypted writes.

**Fix:** promote-and-merge — mutate the existing item's timestamp and move it to index 0 — rather than replace-with-a-bare-copy.

### ⚪ C8. Image dimensions can be pixels or points depending on which read succeeds

`PasteboardMonitor.swift:186`:

```swift
guard let size = ImageProcessor.pixelSize(of: imageData) ?? NSImage(data: imageData)?.size else
```

The first returns **pixels** (ImageIO metadata), the fallback returns **points** (DPI-scaled). A Retina screenshot reports 2560×1600 or 1280×800 depending on whether ImageIO could read the header. That value is displayed in the preview (`ClipboardItem.swift:581-585`) and persisted. Two identical screenshots can show different dimensions.

### ⚪ C9. SVG's dual identity leaks into feature gating

SVG items carry `contentType == .image` (`PasteboardMonitor.swift:353-358`) with bytes in `svgData`. Mostly handled well — the storage layer, exporter, and previews all special-case it. But `Summarizer.canSummarize` (`Summarizer.swift:66-76`) switches on `content` and rejects `.svg` via `default`, even though `plainText` happily returns the markup (`ClipboardItem.swift:551`). Minor, but it's the kind of inconsistency a `case .svg` in a `switch` would have caught — prefer exhaustive switches over `default` on your own enums, precisely so the compiler tells you where to think.

## D. Concurrency, lifecycle, and dead controls

Genuine credit first: **no data races found.** `StoredEntry` value-type snapshots are taken on the main actor before crossing into the `HistoryStore` actor, so the mutable `@MainActor ClipboardItem` never crosses an isolation boundary. The secure-timeout task propagates cancellation correctly instead of the classic `try?`-fires-immediately-on-cancel bug (`ClipboardManager.swift:286-290`). The Carbon event trampoline captures nothing and hops to `@MainActor` with a plain `UInt32` (`HotkeyManager.swift:123-140`). That is the hard stuff, done right.

The problems are in resource lifetime and in error paths that dead-end.

### 🔴 D1. `KeyRecorderView` leaks a global event monitor that swallows every keystroke

`startRecording` installs a local monitor that consumes **all** keyDown events by returning `nil` (`KeyRecorderView.swift:44-50`):

```swift
eventMonitor = NSEvent.addLocalMonitorForEvents(matching: .keyDown) { event in
    handleKeyEvent(event)
    return nil // consume the event
}
```

It is removed only by `stopRecording()`, which runs on Escape, on a successful capture, or on the Cancel button. **There is no `.onDisappear`.**

`KeyRecorderView` lives inside `SettingsView`'s `TabView` (`SettingsView.swift:27-33`) and inside the onboarding flow (`OnboardingView.swift:125-136`). Click "Change", then switch to the Transformations tab — or close the settings window, or press Continue in onboarding — and the view is destroyed while the monitor lives on. From that moment **every keystroke anywhere in the app is swallowed**: the search field, ⌘Q, keyboard navigation, all of it. `NSEvent.removeMonitor` can no longer be called because the token died with the view. Only relaunching fixes it.

While recording, ⌘Q is also consumed (`return nil` happens before any filtering), so the app can't even be quit by keyboard during the recording state.

**Fix:** `.onDisappear { stopRecording() }` closes the acute bug. Structurally, an `NSEvent` monitor is process-scoped state and does not belong in a `View` struct's `@State` — own it in a small `@Observable` recorder object with a `deinit`, or use `NSViewRepresentable` where the AppKit lifecycle gives you real teardown hooks.

> **Lesson:** SwiftUI `View`s are values that get created and destroyed constantly, with no guaranteed teardown callback beyond `.onDisappear`. Any time you put a resource with an unregister requirement — event monitors, observers, timers, file handles — into `@State`, you have created a leak unless you pair it with explicit cleanup. Ask: "what destroys this, and is that guaranteed to run?"

### 🔴 D2. A failed hotkey registration kills the shortcut permanently, and the error is never shown

`HotkeyManager.register` drops the existing registration *before* attempting the new one (`:62-66`):

```swift
if let existingRef = registrations[id]?.hotkeyRef {
    UnregisterEventHotKey(existingRef)
    registrations[id] = nil
}
```

If `RegisterEventHotKey` then fails — the user picked a combination another app or the system already owns, which is exactly what people do when rebinding — the function sets `lastRegistrationError` and returns `false` with `registrations[id]` still `nil` (`:80-86`).

Now the trap: `reregister` early-returns when the slot is empty (`:98-101`):

```swift
func reregister(id: HotkeyID, keyCode: UInt32, modifiers: UInt32) {
    guard let existing = registrations[id] else { return }   // ← permanently nil
    register(id: id, keyCode: keyCode, modifiers: modifiers, callback: existing.callback)
}
```

`reregister` is the **only** path the settings UI uses (`SettingsView.swift:207, 224, 235, 242`). So after one failed rebind, every subsequent attempt — including "Reset to defaults" — is a silent no-op. The user's hotkey is dead until they quit and relaunch.

And they are never told: `lastRegistrationError` (`HotkeyManager.swift:30`) is written in three places and **read nowhere** (verified by grep). The Settings screen shows the shortcut they chose, and nothing works.

**Fix:** (1) attempt the new registration before releasing the old one, or restore the old one on failure. (2) Store the callback separately from the live registration so `reregister` can always retry. (3) Surface `lastRegistrationError` in the settings row — a red caption under the recorder is enough.

> **Lesson:** Two bugs here, and both are about failure paths. First: don't tear down working state before you know the replacement succeeds — acquire, then release. Second: a `private(set) var lastError` with no reader is not error handling, it's error *storage*. If you add an error property, add the view that displays it in the same PR, or you have built a silence machine.

### 🟠 D3. `launchAtLoginError` is also never displayed

Identical shape (`SettingsManager.swift:157`). `SMAppService.register()` throws, the property is set, the toggle reverts itself, and the user watches a switch flip back with no explanation. Zero readers.

### 🟠 D4. `updateIcon(hasItems:)` has no callers — the status bar icon never changes

`StatusBarItemController.updateIcon` (`:26-31`) switches between `clipboard` and `clipboard.fill`, and `StatusBarController` forwards to it (`:63-65`). **Nothing calls the forwarder.** The icon is set once in `setup()` and never updated. A whole (small, nice) affordance is wired up to nothing — and its existence makes a reader assume the feature works.

### 🟡 D5. `TaskLimiter` leaks permits on any early exit and ignores cancellation

Two issues in ~25 lines (`ClipboardManager.swift:613-638`, used at `:319-339`):

```swift
await Self.ocrLimiter.acquire()
let text = await ImageTextExtractor.extractText(from: data)
await Self.ocrLimiter.release()
```

1. **No `defer`.** Today nothing between the two calls can throw or return early, so it happens to be correct. Add one `guard` in the middle during a future edit and you leak a permit; leak two and OCR stops for the process lifetime with no error.
2. **`acquire()` is not cancellation-aware.** `await withCheckedContinuation { waiters.append($0) }` (`:627`) — a cancelled waiting task is never resumed and hangs forever, and `release()` can hand its slot to an already-cancelled waiter.

**Fix:** `defer { await ... }` isn't available for async, so use `withTaskCancellationHandler` plus a `do/defer` around a non-async release, or replace the whole thing with a bounded `TaskGroup` at the call site.

> **Lesson:** Any acquire/release pair without `defer` is a bug waiting for its second edit. The correctness doesn't come from the current code being simple; it comes from making the release unconditional.

### 🟡 D6. Termination flush has no timeout and doesn't stop new work

`applicationShouldTerminate` returns `.terminateLater` and awaits `flushPendingSaves()` (`ClippedApp.swift:102-108`). If the `HistoryStore` actor is blocked — a Keychain prompt, a slow disk — `NSApp.reply(toApplicationShouldTerminate:)` never runs and **the app cannot be quit**. There's no watchdog.

Also, `flushPendingSaves` awaits only the *current* debounce task (`ClipboardHistory.swift:251-255`). An OCR or link-metadata task completing during the flush schedules a fresh debounce that nobody waits for. Monitoring isn't stopped and enrichment tasks aren't cancelled first.

**Fix:** stop the monitor and cancel enrichment before flushing; race the flush against a ~2 s timeout and reply regardless.

### 🟡 D7. `observeScreenSharingPolicy` can miss a change

`withObservationTracking`'s `onChange` fires once, *before* the value updates, and re-arming happens asynchronously inside a `Task` (`ClippedApp.swift:112-122`). A second toggle inside that window is not observed, leaving window `sharingType` stale — i.e. clipboard content visible in a screen share when the user believes they've hidden it. Small window, but this is a privacy control.

**Fix:** re-arm synchronously before the async work, or drive it from the settings `didSet` directly.

### ⚪ D8. `deinit` assumes the main thread

`PasteboardMonitor.deinit` calls `pollTimer?.invalidate()` via `nonisolated(unsafe)` (`:67-71`). `Timer.invalidate()` must be called on the thread that scheduled it. If the last reference is ever released from a background context, this is undefined behaviour. It's correct today because these objects are only released on the main actor — but the comment justifies the `unsafe` on race-freedom grounds and doesn't mention the thread-affinity requirement, which is the actual hazard.

## E. UI, UX, and accessibility

### 🟠 E1. The recovery alert can't be dismissed and loops on repeated failure

`ClipboardPanelView.swift:279-294`:

```swift
.alert(
    "Clipboard history couldn't be opened",
    isPresented: Binding(get: { manager.historyLoadError != nil }, set: { _ in })
) {
    Button("Retry") { Task { await manager.retryHistoryLoad() } }
    Button("Start fresh", role: .destructive) { ... }
}
```

The binding's setter discards dismissal, and neither button has `role: .cancel`. If Retry fails (Keychain still locked — the single most likely case), `loadError` stays non-nil and the alert re-presents immediately. The user's only exit is the destructive option, which — given A2 — is also the one that permanently discards their data. That is a genuinely bad corner to paint someone into.

**Fix:** add a "Later" cancel button that clears the in-memory `loadError` while leaving `saveBlocked` set, so saves stay refused and nothing is destroyed. Surface the recovery state as a persistent banner rather than a modal.

### 🟠 E2. Destructive clears have no confirmation, and the state for one is dead code

`@State private var showClearConfirmation = false` (`ClipboardPanelView.swift:16`) is declared and **never read or written**. Someone intended a confirmation dialog and it was lost in review — the compiler doesn't warn on unused `@State`.

Today, "Clear All" wipes history with a 3-second undo (`:422-430`), and the quick menu's "Clear history" (`:104-109`) wipes it with **no confirmation and no undo at all**. Two paths to the same destructive action with different safety levels is worse than either being consistently applied.

### 🟠 E3. Onboarding reappears on every launch if the window is closed

`hasLaunchedBefore` is set only inside the completion closure passed to `OnboardingView` (`ClippedApp.swift:67-75`), which fires only when the user reaches the final step and clicks "Open Clipped". The window has `.closable` in its style mask (`OnboardingWindowPresenter.swift:24`), so closing it early — the natural response to a five-step wizard — leaves the flag unset and the onboarding returns at every launch, forever.

**Fix:** set the flag when onboarding is *presented*, or observe the window's close.

### 🟡 E4. Two settings windows

The SwiftUI `Settings` scene (`ClippedApp.swift:141-147`, reachable via ⌘,) and `SettingsWindowPresenter` (reached via the panel's gear button) create **separate windows** with separate `SettingsView` instances. They share the underlying `SettingsManager`, so state stays consistent, but the user can have two settings windows open simultaneously. Pick one.

### 🟡 E5. The history window recomputes its dataset ~10× per render

`items(for:)` builds `manager.pinnedItems + manager.items` from scratch on each call (`HistoryWindowView.swift:302-320`), and per render it's called by four sidebar `count(for:)` calls (`:65-68`), `appGroups` (`:294-296`), `displayedItems` (`:322-330`), `selectedItem` (`:332-335`), and `totalCount` (`:290-292`). At 500 items that's ~10 array concatenations plus filters per render, and `.searchable` has no debounce so it repeats on every keystroke.

**Fix:** compute the merged list once into a `let` at the top of `body` and pass it down; debounce the search binding.

### 🟡 E6. Fixed panel geometry versus Dynamic Type

The panel is hard-pinned to 380×420 (`StatusBarController.swift:12-13`, applied at `ClipboardPanelView.swift:240`) while its content uses semantic fonts that scale with the user's text size. Only the empty-state icon uses `@ScaledMetric` (`:26`). At accessibility text sizes rows clip and the bottom bar's seven icon buttons collide. The onboarding window is likewise fixed at 480×400 (`OnboardingView.swift:83`) with no `ScrollView`.

### ⚪ E7. Relative timestamps never refresh

`relativeTimeString(for:)` captures `Date()` at render (`HistoryWindowView.swift:766-769`) with nothing driving re-renders. Leave the history window open and everything is still "2m ago" an hour later. `Text(date, format: .relative(presentation: .named))` self-updates and drops the shared-formatter workaround entirely.

### ⚪ E8. Filter chips don't announce selection

`ContentTypeFilterBar`'s buttons convey selection purely through font weight and background tint (`:29-35`) — no `.accessibilityAddTraits(.isSelected)`. VoiceOver users can't tell which filter is active. Colour-only state also fails the "don't rely on colour alone" guideline.

**Good, and worth noting so nobody regresses it:** the row accessibility work from #102 is right (`.accessibilityAddTraits(.isButton)` + `.accessibilityAction`, `ClipboardItemRow.swift:56-60`), reduce-motion is honoured in three places, thumbnails are cached and downsampled (`ImageProcessor.swift:9-40`), selection is by stable identity rather than index (`ClipboardPanelView.swift:21`), and icon-only buttons consistently carry `.help` plus accessibility labels.

## F. Testing

The suite's *construction* is genuinely good: all Swift Testing structs, no XCTest anywhere, real DI seams via `MockPasteboard` / `MockHistoryStore` / `MockLinkMetadataFetcher`, parameterised argument tables used well, and `HistoryStoreTests` now correctly injects a temp directory (`:13-22`) so it can't delete a developer's real history — that was the right fix. `IntegrationTests` genuinely exercises monitor → ingest → history → store.

The gap is **what** is covered.

### 🟠 F1. Three tests still hit the live network, and two of them assert nothing

`LinkMetadataFetcherTests` fetches `https://example.com` for real at `:9-13`, `:23-32`, and `:88-94`. That's flaky offline, slow in CI, and dependent on a third party's HTML. Worse, two of them don't test what they claim:

- **"Caches fetched metadata"** (`:23-32`) asserts `metadata1.title == metadata2.title`. Two calls to a *non-caching* implementation would also return equal titles. The test passes whether or not the cache exists. To test a cache you must assert the collaborator was called **once** — which requires injecting the fetch, which the current design doesn't allow.
- **"Fetches favicon data"** (`:88-94`) asserts `metadata.title != nil` and never looks at `favicon`. The comment even acknowledges it ("example.com may or may not have a favicon") — at which point the honest move is to delete the test or build a fixture.

**Fix:** extract the network call behind a seam so the cache and dedup logic can be tested against a stub. The pure `IPLiteral` tests (`:60-86`) show the team already knows how to do this — apply the same thinking one layer up.

> **Lesson:** A test whose assertion would pass against a deliberately broken implementation is worse than no test: it's a false statement about your coverage, and it will be cited as a reason not to write the real one.

### 🟠 F2. `SettingsManagerTests` reads the developer's own preferences

Four tests construct the real `SettingsManager()` (`:7, 13, 19, 26`), whose init reads `UserDefaults.standard` and queries `SMAppService.mainApp.status` (`SettingsManager.swift:202-262`). A developer who has changed their history size or turned off secure mode fails the suite; CI passes because CI is clean. That's the worst kind of flake — one that only reproduces on the machine of whoever is trying to ship.

`OnboardingSeederTests` already demonstrates the fix (a per-test `UserDefaults(suiteName:)`). `SettingsManager` needs the same injection its collaborators got.

### 🟠 F3. The highest-risk code has no tests

Nothing covers:

- **The persistence-toggle path (A1)** or **the retry-merge path (A2)** — the two data-loss bugs in this review. Both are pure `ClipboardHistory` + `MockHistoryStore` tests; neither needs a filesystem.
- **`HotkeyManager.register` failure handling (D2)** — `formatShortcut` and `keyName` are pure functions with no Carbon dependency at all and could be tested today; the registration state machine needs a thin protocol over `RegisterEventHotKey`.
- **`TaskLimiter` (D5)** — a self-contained actor, trivially testable, currently zero tests.
- **`ScreenshotWatcher`** — `MockScreenshotWatcher` exists in `Mocks.swift:239-284` and is referenced by **no test**. A mock with no consumers is a strong signal that a planned test was never written.
- **`Summarizer.canSummarize`**, **`FileExporter.suggestedBaseName`** slug edge cases (empty text, all-punctuation, CJK), **`ImageTextExtractor`**.

### 🟡 F4. The secure-timeout test can't observe the behaviour it names

`IntegrationTests` "secureMode + timeout > 0 ingests but does not persist" sets a timeout long enough that the removal can never fire during the test. So the *ingest* half is covered and the *removal* half — including the pinned-item hole in C3 and the cancellation-suppression logic — is not. Inject the `Duration` (or a clock) so the test can drive it to zero.

> **Lesson:** If a behaviour is time-dependent, inject the time. `Task.sleep(for:)` with a hardcoded interval is untestable by construction, and "we'll test it manually" means "it is untested."

## G. Repo, build, and process

### G1. Three stale review documents are committed at the repo root

`CODE_REVIEW.md` (394 lines), `PRINCIPAL_REVIEW.md` (247), and `code-review.md` (1,229) are all tracked, all overlapping, and all stale — PR #102 fixed much of what they describe, but nothing marks them as resolved. `CODE_REVIEW.md` even opens by explaining that it supersedes an earlier version of itself.

The cost is real: a new engineer reads them as current, and re-investigates fixed bugs. Review findings have a lifecycle — open, fixed, verified — and a markdown file in git has no way to express it.

**Fix:** file the surviving findings as GitHub issues (which this project's own conventions already call for), delete the three documents, and keep design *decisions* in docs rather than defect lists.

### G2. The generated Xcode project is committed alongside its generator

`Clipped/project.yml` is declared "source of truth" in `CLAUDE.md`, yet `Clipped/Clipped.xcodeproj/project.pbxproj` is tracked. Every `make generate` produces a diff, `.pbxproj` merge conflicts are notoriously unresolvable, and nothing verifies the two agree. CI runs `make generate` before testing but never checks whether the regenerated project matches the committed one.

**Fix:** either gitignore the `.xcodeproj` and have every entry point generate it, or drop XcodeGen. Add a CI step that regenerates and fails on a dirty tree.

### G3. CI has no coverage floor and no release-configuration build

`ci.yml` runs lint plus a Debug `make test`. Nothing measures coverage, and Release-only failures (optimiser-sensitive code, `#if` mismatches — relevant here given `Summarizer`'s `canImport(FoundationModels)` gating) would first appear in the release workflow.

### G4. The README's encryption claim is stronger than the default configuration

`README.md:50` states that "Time Machine snapshots, cloud backups, and forensic disk access only ever see ciphertext." Two qualifications:

- **Persistence is off by default.** `persistAcrossReboots = UserDefaults.standard.bool(forKey:)` (`SettingsManager.swift:203`) with no override, so a fresh install stores nothing. The headline "Encrypted at rest" feature is inert until the user opts in, and the Settings security footer (`SettingsView.swift:145-148`) describes the encryption unconditionally, which reads as "this is happening now."
- Snapshots taken **before** the encrypted-storage upgrade contain the old plaintext `history.json` forever, and per A4 that file can also be deleted without ever having been migrated.

**Fix:** say "when persistence is enabled" in both places, and note the pre-1.x snapshot caveat in the upgrade notes.

## H. What is genuinely good

A review that lists only faults teaches juniors that good work is invisible. It isn't — these are things to copy:

- **The actor boundary is correct.** `StoredEntry` is a value type, snapshotted on the main actor, and it is the only thing that crosses into `HistoryStore`. The mutable `@MainActor ClipboardItem` never leaves its isolation domain. This is what Swift 6 concurrency is supposed to look like, and most codebases get it wrong.
- **Cancellation is handled deliberately.** `ClipboardManager.swift:286-290` catches the sleep's cancellation error and *returns* rather than using `try?`, with a comment explaining precisely why. That's a footgun most people trip over once.
- **The SSRF filter is a serious piece of engineering.** Canonicalising with `inet_pton`, unwrapping IPv4-mapped/NAT64 embeddings, validating every resolved address, failing closed, and — crucially — documenting the residual redirect risk honestly instead of pretending it's solved.
- **Crypto choices are right.** ChaChaPoly AEAD with per-message nonces, `WhenUnlockedThisDeviceOnly`, key never on disk, `0o600` temp files with `replaceItemAt`, `0700` directories.
- **`SVGDetector` bounds its input** to 2 KB before sniffing (`ClipboardItem.swift:630-638`), and the detector inputs are now capped at 100k chars. The instinct to treat input size as adversarial is present — it just needs to reach the screenshot path too.
- **Signpost instrumentation with a documented table** (`Signposts.swift:10-20`) kept in sync with `CLAUDE.md`. Very few side projects can be profiled in Instruments out of the box.
- **The presenter split** (`Sources/Services/Presenters/`) turned a 400-line `StatusBarController` into a 116-line facade over five focused types, without breaking call sites.
- **Comments explain *why*, not *what*** — the `NSHostingController.parent` exclusivity note (`ClipboardPanelPresenter.swift:34-37`) and the non-`.nonactivatingPanel` rationale (`:128-131`) are exactly the comments worth writing: they record a debugging session so nobody repeats it.

## I. If I could fix only ten things, in this order

1. **A1** — load on the persistence toggle; make `save()` refuse to write when no load has been attempted. *(Silent, total data loss on an ordinary user action.)*
2. **A2** — merge on retry instead of discarding, and clear `saveBlocked` only after the merge commits. *(The recovery path destroys the data it recovered.)*

## J. Teaching notes for the team

Four habits, drawn from the findings rather than from general principle. Each maps to specific bugs above.

**1. When you add a check, enumerate everything that can reach the data.**
The reveal gate (B1), the ingestion policy (B3), the export paths (B2), and the save guard (A1) all failed the same way: correct on the path the author was looking at, absent on the path someone else added. Before merging a protection, grep for every other reader and writer of the same field. If there are three, you need one shared implementation, not three correct copies — because three copies means the fourth won't be.

**2. Failure paths need a consumer, not just a value.**
`lastRegistrationError`, `launchAtLoginError`, and the dropped-item path in A5 all record a problem into a variable nobody reads. Storing an error is not handling one. The rule: an error property and the view that displays it belong in the same pull request. If you're not ready to show it, log it at `.error` level at minimum, so it exists somewhere a human might look.

**3. Acquire before you release; make release unconditional.**
D2 releases the working hotkey before acquiring the replacement and leaves the user with nothing. D5 pairs acquire and release without a `defer` and is correct only by accident of the current code shape. A1 and A4 delete or overwrite before confirming the replacement succeeded. Same principle every time: **the state you're replacing is valuable until the replacement is proven.**

**4. A helper carries the assumptions of the code it was born in.**
`applyLoaded`'s `if items.isEmpty` (A2) is not a general merge rule; it means "we are still booting." Reused from `retryHistoryLoad`, that assumption is silently false and costs the user their history. When you reuse a function from a new lifecycle moment, read it looking for assumptions about *when* it runs — and if you find one, either parameterise it or name the function after the moment.

And a fifth, which is really the whole review compressed:

> **A feature is not done when the happy path works. It is done when it round-trips through persistence, survives a hostile or oversized input, degrades safely when a dependency is unavailable, tells the user when it can't, and has a test that fails if any of that regresses.**

The craft here is real. Every finding above is an edge, not a foundation. That's the good position to be in — it just needs carrying all the way out to the edges.
